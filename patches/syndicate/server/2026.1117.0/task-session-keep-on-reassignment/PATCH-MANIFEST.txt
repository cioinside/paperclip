What this fixes
---------------
Paperclip restarts the agent's OpenCode session on most wakes, and OpenCode
generates the session title once per session — so every restart costs one extra
"small" request. The dominant reset reason on this instance is the wake reason
`issue_assigned`: a human reply on a task that was parked in review (the task is
assigned to the human while it waits) hands the task back to the agent, and the
server reports that hand-back as an assignment. `shouldResetTaskSessionForWake`
resets the task session for `issue_assigned`, so the OpenCode session — and its
title — restarted on every human reply.

Measured on this instance (run logs, /root/.paperclip/instances/default/data/run-logs):
  "Skipping saved session resume for task ... because wake reason is issue_assigned"
  242 occurrences — every other reset reason is a real config change
  (83 adapter/adapter-config/secrets, 27 forceFreshSession, 25 instructions,
  13 model changes, ...).
Example: SYN-341 (db0ce455), two comment wakes 9 minutes apart produced two
different OpenCode sessions (ses_e0b303816 -> ses_e0b28bbd6); opencode.log
shows exactly one title call per session (290 of 340 sessions have one).

Change
------
In prepareHeartbeatSession (services/heartbeat/session-preparation.js) the
`issue_assigned` reset no longer applies when the task already carries a
session:

    const reassignedTaskWithSession = taskSession != null &&
        readNonEmptyString(context.wakeReason) === "issue_assigned" &&
        context.forceFreshSession !== true;
    const resetTaskSession = context.workspaceSelectionChanged === true ||
        (shouldResetTaskSessionForWake(context) && !reassignedTaskWithSession) ||
        sessionConfigFreshness.reset;

Scope of the exemption:
  * first assignment of a task to an agent (no task session yet) -> unchanged,
    the session still starts clean;
  * a task that already has a session -> the session is kept and OpenCode
    resumes it, so no second title generation;
  * forceFreshSession, a changed model, a changed adapter/instructions/
    workspace config, and workspaceSelectionChanged still reset the session;
  * other wake reasons (issue_commented, execution_approval_requested, ...)
    are untouched — only `issue_assigned` is exempted.
