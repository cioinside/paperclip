What this fixes
---------------
Every tools/call through the MCP protocol route was cut at 10 seconds,
whatever the tool needed. The MCP branch of `handleMcpGatewayProtocol`
called `toolGateway.executeTool({...})` without a `timeoutMs`, and the
service then fell back to `DEFAULT_TOOL_TIMEOUT_MS = 10_000`
(services/tool-gateway.js). The non-MCP route has always forwarded the
caller's timeout (`routes/tool-gateway.js`: `timeoutMs: body.timeoutMs`),
and the service clamps any timeout to at most 60s, so only the MCP path
was affected.

The client cannot fix this from the outside: an MCP client's own timeout
(the `"timeout": 60000` in the agent's opencode MCP config) is a client-side
abort and never reaches the gateway. Measured on this instance (SYN-807):
`ragmir_write_file` (1.5 MB) -> HTTP 504 `{"reasonCode":"tool_timeout"}`
after 11.96s, with the file already written on disk.

Change
------
1. `routes/tool-gateway.js`, MCP `tools/call` branch: forward the caller's
   timeout, exactly like the non-MCP route already does:

       timeoutMs: body.timeoutMs,

2. `services/tool-gateway.js`: a connection may agree a longer budget for
   its own tools. When the caller did not ask for a timeout
   (`input.timeoutMs === undefined`), the MCP transports take the budget
   from the connection row they already loaded:

       export function connectionToolTimeoutMs(connection, tool) {
           const value = asRecord(connection?.config)?.toolTimeoutMs;
           return Number.isFinite(value) ? timeoutMs(value, tool) : undefined;
       }

   applied in `executeRemoteHttpTool` (mcp_remote_http / provider_rest) and
   in `executeLocalStdioTool` (mcp_local_stdio) — the two paths that carry
   the upstream call's deadline.

Configuration
-------------
`tool_connections.config.toolTimeoutMs` (number, milliseconds) is the agreed
budget for a connection. It is clamped by the existing `timeoutMs()` helper
to 1..60000 ms, so the gateway ceiling (60s, the same one the non-MCP route
uses) still applies. `config` is a free-form record
(`toolTransportConfigSchema = z.record(z.string(), z.unknown())`), so the
key needs no schema change; it is set through the normal connection update
route (`PUT /tool-connections/:connectionId`, `config` is replaced
wholesale, so keep the existing keys).

Defaults are unchanged: a connection without `config.toolTimeoutMs` keeps
the 10s default, and an MCP caller that sends no timeout keeps it too.
