change           In `answerQuestions` (services/issue-thread-interactions.js) the
                 answer transaction now hands the task back to the agent that asked
                 the question before the delivery row is queued:
                   - the locked issue row also selects assignee_agent_id/assignee_user_id
                   - when a human answered, the interaction has a created_by_agent_id,
                     the task has no agent assignee but a human assignee, and the task
                     is in_review or in_progress: issue.assignee_agent_id =
                     interaction.created_by_agent_id, issue.assignee_user_id = NULL
                     (status is NOT changed)
                   - activity publications of that update are published after the
                     transaction commits
                 This mirrors the existing confirmation-accept path
                 (`shouldReturnIssueToCreatorOnAccept` + `issueService(db).update`),
                 which already returns a task to the interaction creator. The status is
                 left alone on purpose: the continuation auto-checkout in
                 services/heartbeat.js claims only in_progress/in_review tasks, so
                 moving the task to `todo` would make the continuation run stale and
                 cancel it.
change2          SYN-788: the SYN-761 hand-back stopped at the assignee. A task
                 parked under a human review stage keeps that stage participant in
                 `executionState`, and the run-dispatch gate
                 (`modules/run-dispatch/domain/policy.js` ->
                 `decideReviewParticipant`) refuses to start the resumed agent run
                 while another principal holds the task: the queued continuation run
                 was cancelled with `issue_review_participant_changed`
                 (live evidence, SYN-782, 2026-11-22T20:00:33Z:
                 paperclip.service log "claimQueuedRun: withheld queued run at the
                 execution gate", runId 6bfb3c2c-027a-42dd-be98-e39f588abfb9).
                 The same task then bounces back to the human on the agent's next
                 PATCH: the execution-policy transition sees assignee != stage
                 participant (`stageStateDrifted`) and re-pends the stage to the
                 human. The hand-back therefore also releases the stage hold, the
                 way a changes-requested decision does:
                   - the locked issue row also selects execution_state
                   - when the stage holds the task (status in_review, executionState
                     status pending, participant is not the asking agent):
                     status -> in_progress, executionState.status ->
                     "changes_requested" (stage id, stage type, participant,
                     returnAssignee and completedStageIds are preserved for the next
                     round), lastDecisionOutcome -> null, changesRequestedCount -> 0
                   - a task without a stage hold keeps the SYN-761 behaviour
                     (assignee only)
                 The released state passes the gate and the continuation checkout
                 (`services/heartbeat.js` -> `shouldAutoCheckoutIssueForWake`
                 refuses a pending executionState).
